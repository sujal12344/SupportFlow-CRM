# Interview Preparation Guide - SupportFlow CRM

## 🎯 Core Questions & Answers

### 1. **Tell me about your project.**

**Answer (30 seconds)**:
"I built SupportFlow CRM, a full-stack customer support ticketing system. Users can create tickets with customer information, search and filter tickets in real-time, and update ticket status with timeline comments. 

I used Next.js 16 with React 19 for the frontend, Supabase PostgreSQL for the database, and Zod for type-safe validation. The app is deployed on Vercel and includes a demo mode fallback for testing without database connection.

Key features include live search with debouncing, character counters with client-side validation, and a responsive design that works on mobile and desktop."

---

### 2. **What tech stack did you use and why?**

**Answer**:
- **Next.js 16**: Server-side rendering, built-in API routes, file-based routing, no separate backend needed
- **React 19**: Latest features, better performance, component-based architecture
- **Supabase**: PostgreSQL database with auto-generated REST API, free tier, easy setup
- **Tailwind CSS v4**: Utility-first styling, fast development, consistent design system
- **Zod**: Runtime type validation, type-safe with TypeScript, better error messages
- **TypeScript**: Type safety, better IDE support, catch errors at compile time

**Why this stack?**  
Modern, scalable, and follows industry best practices. Easy to deploy and maintain.

---

### 3. **Explain your database schema.**

**Answer**:
"I have two tables:

**tickets table**:
- `ticket_id` (unique, e.g., TKT-1001) - Auto-generated by database trigger
- `customer_name`, `customer_email` - Customer details
- `subject`, `description` - Issue information
- `status` - ENUM (Open, In Progress, Closed)
- `created_at`, `updated_at` - Timestamps

**notes table**:
- `ticket_id` (foreign key) - Links to tickets
- `note_text` - Comment content
- `created_at` - When comment was added

The relationship is one-to-many: one ticket can have multiple notes."

---

### 4. **How does your search functionality work?**

**Answer**:
"I implemented live search with a 300ms debounce to avoid excessive API calls.

**Flow**:
1. User types → `setSearch(value)`
2. `useEffect` with `setTimeout` → waits 300ms
3. Updates `debouncedSearch` state
4. Another `useEffect` watches `debouncedSearch`
5. Triggers API call: `GET /api/tickets?search=query`
6. Backend searches across: ticket ID, customer name, email, subject, and description
7. Returns filtered results

**Why debounce?**  
If user types "John", without debounce we'd make 4 API calls (J, Jo, Joh, John). With debounce, we wait until they stop typing, making only 1 call."

---

### 5. **How did you implement validation?**

**Answer**:
"I implemented both client-side and server-side validation:

**Client-Side** (Better UX):
- Check field lengths before submission
- Email regex validation
- Show character counters (e.g., 45/150)
- Display specific error messages immediately

**Server-Side** (Security):
- Zod schema validation on all API endpoints
- Validates data types, formats, and constraints
- Returns 400 with specific error messages
- Prevents invalid data from reaching database

**Example Zod schema**:
```typescript
ticketSchema = z.object({
  customer_name: z.string().trim().min(2).max(100),
  customer_email: z.string().trim().email(),
  subject: z.string().trim().min(3).max(150),
  description: z.string().trim().min(5).max(3000)
})
```

Never trust client-side validation alone - always validate on server!"

### 6. **How does state management work in your app?**

**Answer**:
"I used React Context API for global state and local useState for component state.

**Global State** (TicketContext):
- Ticket statistics (total, open, in progress, closed)
- Demo mode detection
- Shared across all components

**Local State**:
- Search input, filter selections
- Form data (create ticket)
- Loading states, error messages

**Why Context instead of Redux?**  
For this app size, Context API is sufficient. Redux would be overkill. Context provides what we need: shared stats and a refresh function."

### 7. **Explain your API structure.**

**Answer**:
"I built 4 REST API endpoints using Next.js API routes:

1. **POST /api/tickets** - Create new ticket
   - Validates with Zod
   - Returns ticket_id and created_at

2. **GET /api/tickets?status=&search=** - List tickets
   - Optional query params for filtering
   - Returns array of tickets

3. **GET /api/tickets/[id]** - Get single ticket
   - Returns ticket with notes array
   - Returns 404 if not found

4. **PUT /api/tickets/[id]** - Update ticket
   - Can update status and/or add notes
   - Returns updated_at timestamp

**Error Handling**:
- Zod validation errors → 400 with specific message
- Not found → 404
- Server errors → 500 with generic message (no internal details exposed)"

---

### 8. **How did you handle errors?**

**Answer**:
"I implemented comprehensive error handling:

**API Level**:
- Try-catch blocks in all endpoints
- Zod catches validation errors → 400 status
- Database errors → 500 status
- Not found → 404 status
- Never expose internal error details to client

**Frontend Level**:
- Display user-friendly error messages
- Show loading states during operations
- Disable buttons while submitting
- Toast notifications for success/failure

**Example**:
```typescript
try {
  const validated = ticketSchema.parse(body);
  // Process...
} catch (error) {
  if (error instanceof ZodError) {
    return NextResponse.json(
      { error: error.issues[0].message },
      { status: 400 }
    );
  }
  return NextResponse.json(
    { error: 'Internal server error' },
    { status: 500 }
  );
}
```"

### 9. **What is the demo mode fallback?**

**Answer**:
"I implemented a dual-mode system:

**Supabase Mode** (Production):
- Uses real PostgreSQL database
- Requires environment variables
- Persistent data storage

**Demo Mode** (Fallback):
- Uses in-memory JavaScript array
- Works without database connection
- Pre-seeded with sample data
- Perfect for testing and demos

**Detection Logic**:
```typescript
const isDemoMode = () => {
  return !process.env.SUPABASE_URL || !process.env.SUPABASE_ANON_KEY;
}
```

All database functions (`getTickets`, `createTicket`, etc.) check this flag and route to appropriate implementation.

**Why?**  
Ensures app always works, even if database is down. Great for demos and local development."

### 11. **What challenges did you face?**

**Answer**:
"Three main challenges:

**1. React Hooks ESLint Errors**:
- Issue: `setState` in `useEffect` causing cascading renders warning
- Solution: Refactored to move data fetching logic inside useEffect, removed function from dependency array

**2. TypeScript Zod Integration**:
- Issue: `error.errors` property doesn't exist on ZodError
- Solution: Use `error.issues` instead (correct Zod API)

**3. Build Optimization**:
- Issue: Large bundle size initially
- Solution: Used dynamic imports, optimized images, removed unused dependencies

These challenges taught me to read documentation carefully and debug systematically."

### 13. **Walk me through creating a ticket.**

**Answer**:
"Here's the complete flow:

**User Action**:
1. Clicks 'Create Ticket' button in sidebar
2. Drawer slides in from right

**Client Validation**:
3. User fills form (name, email, subject, description)
4. Character counters show limits (e.g., 45/150)
5. Client validates on submit:
   - Check required fields
   - Validate email format
   - Check length constraints
   - Show error if invalid

**API Call**:
6. `POST /api/tickets` with form data
7. Server validates with Zod schema
8. If invalid → return 400 + error message
9. If valid → insert into database

**Database**:
10. PostgreSQL trigger auto-generates `ticket_id` (TKT-1004)
11. Sets `status = 'Open'`, adds timestamps
12. Returns created ticket

**UI Update**:
13. Close drawer
14. Show success toast
15. Refresh stats in context
16. Navigate to new ticket detail page

Total time: ~500ms for the whole flow."

### 14. **How does filtering work?**

**Answer**:
"I implemented two types of filters:

**Status Filter** (URL-based):
- User clicks status card or filter button
- Updates URL: `/?status=Open`
- `useSearchParams` reads URL
- Triggers API call: `GET /api/tickets?status=Open`
- Backend filters with SQL WHERE clause
- Results update on page

**Search Filter** (Debounced):
- User types in search box
- 300ms debounce timer
- Combines with status: `?status=Open&search=john`
- Backend uses OR query across multiple fields
- Returns matching tickets

**Why URL for status?**  
- Shareable links
- Browser back/forward works
- Bookmark filtered views
- Better UX

**Backend Query**:
```sql
SELECT * FROM tickets 
WHERE status = 'Open' 
AND (
  customer_name ILIKE '%john%' OR
  customer_email ILIKE '%john%' OR
  subject ILIKE '%john%'
)
ORDER BY created_at DESC
```"

**Answer**:
"Five scaling strategies:

1. **Database Optimization**:
   - Add indexes on frequently queried fields (ticket_id, status, created_at)
   - Database connection pooling
   - Read replicas for queries

2. **Caching**:
   - Redis for ticket stats
   - CDN for static assets
   - Browser caching headers

3. **API Optimization**:
   - Implement pagination (50 tickets per page)
   - Rate limiting to prevent abuse
   - GraphQL for flexible queries

4. **Infrastructure**:
   - Auto-scaling serverless functions
   - Load balancing
   - Monitoring and alerts

5. **Code Optimization**:
   - Code splitting
   - Lazy loading
   - React.memo for expensive components

Current architecture on Vercel + Supabase can handle thousands of users with minimal changes."

### 17. **Security considerations in your app?**

**Answer**:
"I implemented several security measures:

1. **Input Validation**:
   - Zod validation prevents injection attacks
   - Trim and sanitize all inputs
   - Length limits prevent DoS

2. **API Security**:
   - Never expose internal errors
   - Use environment variables for secrets
   - HTTPS only (Vercel enforces)

3. **Database Security**:
   - Parameterized queries (Supabase handles)
   - Row-level security policies
   - No direct database access from client

4. **XSS Prevention**:
   - React automatically escapes output
   - No dangerouslySetInnerHTML used

5. **CSRF Protection**:
   - Same-origin policy
   - API tokens if auth added

**What's missing (would add in production)**:
- Rate limiting
- Authentication & authorization
- Audit logs
- Security headers (CSP, X-Frame-Options)"
